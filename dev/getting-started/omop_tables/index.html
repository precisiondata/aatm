    From notes to OMOP tables

    This page shows how to turn clinical notes into rows of OMOP CDM tables. You describe what to find in the notes and where each piece goes in the table; AATM extracts it with an LLM, codes it with the OMOP vocabularies and fills the rows as far as the notes allow.

    Five tables are supported: measurement (scores, lab results), observation (smoking, family and medical history, and other facts), condition_occurrence (diagnoses, signs and symptoms), drug_exposure (drugs prescribed, given or taken) and device_exposure (implants, equipment and supplies).

    If you have not extracted entities from a note before, read the Information extraction quick start first: this page builds on its entity definitions.

    Before you start

    1. Install AATM (Installation).
    2. Download the OMOP vocabularies from Athena. The predefined definitions on this page use SNOMED, LOINC and UCUM (units), so include at least those three.
    3. Run aatm init (CLI quick start). It builds the local vocabulary database (.aatm/omop.db), which every example on this page reads, and the search index the terminology mapper uses. Note the embedding model you choose (for example text-embedding-3-small): you pass the same name to the mapper later.
    4. Set an API key for the model provider, e.g. OPENAI_API_KEY (Environment variables).

    Which definitions need what

    Definition Table Needs the terminology mapper?
    ecog_performance_status measurement no
    smoking_status observation no
    lab_results measurement yes, to code test names
    family_history observation yes, to code conditions
    medical_history observation yes, to code conditions
    condition_occurrence condition_occurrence yes, to code conditions
    drug_exposure drug_exposure yes, to code drugs
    device_exposure device_exposure yes, to code devices

    Definitions without the mapper only need the vocabulary database and an LLM, so they are the easiest way to start.

    Key terms

    You do not need to know OMOP well to follow this page, but these words come up often.

    Term Meaning
    CDM table A table of the OMOP Common Data Model, e.g. measurement. Each row is one fact about a patient.
    Concept An entry of the OMOP vocabularies, e.g. Body weight. Columns ending in _concept_id hold concept ids, numbers such as 3025315.
    Vocabulary and code Where a concept comes from and its code there, e.g. LOINC 29463-7. On this page codes are written LOINC:29463-7.
    Standard concept The concept OMOP uses for analysis when several mean the same thing. *_concept_id columns must hold standard concepts, from any vocabulary. A non-standard concept usually maps to a standard one.
    Domain The kind of concept: Measurement, Observation, Condition, Unit... Each column expects certain domains, e.g. measurement_concept_id takes Measurement concepts.
    Source value The text as written in the note, kept next to the code, e.g. measurement_source_value = "ECOG 4".
    0 and NULL 0 means "there is a value, but it has no concept". Empty (NULL) means "nothing there".

    Your first run

    This uses the predefined ECOG performance status definition, which needs no mapper.

    ecog_to_omop.py
    import asyncio

from aatm.omop import ClinicalNote, OmopExtractionPipeline

pipeline = OmopExtractionPipeline("ecog_performance_status", model_id="openai/gpt-5-mini")

notes = [
    ClinicalNote(
        text="Assessment 05/12/2025\nOncology follow-up. Bedbound, ECOG 4.",
        note_id=107,
        person_id=3,
        note_date="2025-06-01",
        visit_occurrence_id=507,
    ),
]

tables = asyncio.run(pipeline(notes))
measurement = tables["measurement"]
print(measurement.dropna(axis=1, how="all").to_string())  # only the filled columns

    Scripts and notebooks

    The pipeline is asynchronous. In a script, wrap the call in asyncio.run(...) as above. In a Jupyter notebook, write tables = await pipeline(notes) instead.

    The table has every column of the CDM measurement table; dropna leaves out the empty ones when printing:

    measurement_id person_id measurement_concept_id measurement_date measurement_type_concept_id value_as_number value_as_concept_id visit_occurrence_id measurement_source_value measurement_source_concept_id value_source_value
    1 3 36305384 2025-05-12 32858 4.0 4174251 507 ECOG 4 4308014 4

    Reading the result

    • measurement_id is generated, numbered from 1.
    • person_id and visit_occurrence_id come from the ClinicalNote, not from the text. They identify the patient and visit in your database, which the note cannot know.
    • measurement_concept_id 36305384 is the standard concept ECOG Performance Status score (LOINC 89247-1).
    • measurement_date is 2025-05-12, the assessment date written in the note. When a note gives no date, the note date (2025-06-01) is used instead.
    • measurement_type_concept_id 32858 means NLP: the row was derived from text.
    • value_as_number 4.0 and value_as_concept_id 4174251 (ECOG performance status - grade 4) are the grade, as a number and as a concept.
    • measurement_source_value and value_source_value keep what the note said.

    ClinicalNote takes the note text and the values that come with the note: person_id, note_id, note_date, visit_occurrence_id, visit_detail_id and provider_id. All but text are optional; columns that need a missing value stay empty and are reported (see Issues). You can also pass plain strings instead of ClinicalNote objects.

    What you get back

    pipeline(notes) returns an OmopTables object:

    tables["measurement"]                                 # the rows, as a pandas DataFrame
tables.to_dataframes(provenance=True)["measurement"]  # plus where each row came from
tables.issues_dataframe()                             # what could not be filled, and why
tables.mappings_dataframe()                           # how extracted text was coded
tables.extraction_results                             # the extractor's raw output

    With provenance=True, each row gets extra columns (_note_id, _entity_id, _text, _start, _end) pointing at the exact words of the note it was built from, so every row can be checked by a person.

    Issues

    Rows are always returned, even when some columns could not be filled. Each gap is listed in tables.issues_dataframe(), with the row, the column, a reason and a detail.

    Reason Meaning What to do
    missing_required A column the CDM requires is empty, e.g. person_id Pass it in the ClinicalNote
    unparsable_date A date is not a full date, e.g. "on admission". The next source (often the note date) was used Usually nothing; check the detail
    imputed_date_parts A date had no day or month, e.g. "March 2024", and was read as 2024-03-01 Decide if day-level precision matters
    unmapped_label The model chose a label that has no concept; 0 was stored Add the label to concepts, or accept 0
    unmapped No standard concept was found for a text, e.g. the unit "lb"; 0 was stored Review in mappings_dataframe()
    low_confidence The mapper's score was below your min_score; 0 was stored Review the candidate in mappings_dataframe()
    domain_mismatch A coded concept is not of the domain the column expects Review the mapping
    invalid_value A value does not fit its column, e.g. text that is not a number Check the extracted text
    truncated A text was longer than its column (50 characters for *_source_value) Usually nothing
    multiple_children A mention had two children of the same kind, e.g. two dates; the first was used Check the note
    single_date The note gave only an end date, earlier than the fallback start date (often the note date); the end date was used for both, as the CDM allows Usually nothing

    Write your own: body weight, step by step

    This walkthrough builds a definition from scratch: body weight, stored in the measurement table with its unit. It needs no mapper.

    1. Describe what to extract

    An entity definition says what the model should find. Body weight has a value and a unit, so they are children of the weight mention (see Writing entity definitions):

    body_weight.yaml
    - name: Body weight
  key: body_weight
  definition: >
    The patient's measured body weight: the word for weight, the value and the unit,
    copied as written, e.g. "weight 72 kg" or "Wt: 158 lb". Stop at the unit: no
    words or punctuation after it. Does not include target or ideal weights, weight
    changes such as "lost 5 kg", or the weight of anyone other than the patient.

- name: Weight value
  key: weight_value
  definition: The number of a body weight, without the unit, e.g. "72" from "weight 72 kg".
  has_parent: true
  parent_key: body_weight

- name: Weight unit
  key: weight_unit
  definition: The unit of a body weight, copied as written without punctuation, e.g. "kg" or "lb".
  has_parent: true
  parent_key: body_weight

    2. Say where each value goes

    Add an omop block to the top-level entity. Each line names a column of the measurement table and where its value comes from:

    body_weight.yaml (first entity)
    - name: Body weight
  key: body_weight
  definition: >
    ...
  omop:
    table: measurement
    fields:
      person_id: {from: context.person_id}               # from the ClinicalNote
      measurement_concept_id: {concept: "LOINC:29463-7"}  # Body weight, always the same
      measurement_date: {from: context.note_date}
      measurement_type_concept_id: {value: 32858}         # NLP
      measurement_source_value: {from: text}              # the words of the mention
      value_as_number: {from: child.weight_value, as: float}
      unit_concept_id: {from: child.weight_unit, lookup: UCUM}  # "kg" -> kilogram
      unit_source_value: {from: child.weight_unit}

    The omop block is never sent to the model: it only tells AATM how to fill the table. You can check what the model will read with definitions.to_prompt_str().

    3. Check the codes before spending model calls

    from aatm.data_models.extractors import EntityDefinitions
from aatm.omop import OmopTableBuilder

definitions = EntityDefinitions.from_yaml("body_weight.yaml")
OmopTableBuilder(definitions).describe_concepts()
    entity column label code concept_id concept_name vocabulary_id domain_id
    body_weight measurement_concept_id LOINC:29463-7 3025315 Body weight LOINC Measurement

    Loading the file and creating the builder already check a lot: unknown columns, typos in child. or attribute. names, codes missing from the vocabulary, and non-standard concepts all fail here, with a message saying what is wrong (see Troubleshooting).

    4. Run it

    import asyncio

from aatm.omop import ClinicalNote, OmopExtractionPipeline

notes = [
    ClinicalNote(text="Weight 72 kg today. Goal weight 65 kg.", person_id=1, note_date="2025-06-01"),
    ClinicalNote(text="Wt: 158 lb. Lost 5 lb since March.", person_id=2, note_date="2025-06-02"),
]

pipeline = OmopExtractionPipeline(definitions, model_id="openai/gpt-5-mini")
tables = asyncio.run(pipeline(notes))
tables["measurement"]
    measurement_id person_id measurement_concept_id measurement_date measurement_type_concept_id value_as_number unit_concept_id measurement_source_value unit_source_value
    1 1 3025315 2025-06-01 32858 72.0 9529 Weight 72 kg kg
    2 2 3025315 2025-06-02 32858 158.0 0 Wt: 158 lb lb

    The goal weight and the weight loss were left out, as the definition asks.

    5. Read the issues

    tables.issues_dataframe()
    row_id column reason detail
    2 unit_concept_id unmapped No concept for 'lb' with a UCUM code lookup; stored 0

    "kg" is a UCUM code, so it was found (kilogram, 9529). "lb" is not: UCUM writes pounds as [lb_av]. The row is kept with unit_concept_id = 0, which the CDM uses for "there is a unit, but it is not mapped", and unit_source_value keeps "lb".

    Iterate on real notes

    Most fixes are in the wording of the definitions. The first version of this example said only "copied as written", and the model returned "Weight 72 kg today." and "lb.". Adding "Stop at the unit: no words or punctuation after it" fixed both.

    Reference: the omop block

    Column sources

    Each column has one source:

    Source Value Example
    {from: text} The words of the mention "ECOG 4"
    {from: attribute.<key>} The label the model chose for an attribute "4"
    {from: child.<key>} The text of the mention's child with that key "05/12/2025"
    {from: context.<name>} A field of the ClinicalNote person_id
    {value: <constant>} A fixed value 32858
    {concept: "<VOCABULARY>:<code>"} The concept id of a code "LOINC:29463-7"

    A list of sources is tried in order, and the first that gives a value wins. The ECOG definition uses this for the date: the assessment date if the note states a full one, else the note date:

          measurement_date:
        - {from: child.assessment_date, as: date}
        - {from: context.note_date}

    Options

    Option Use with Effect
    as: int, float, str or date from: Convert the text. Dates are read from text such as "05/12/2025" or "March 2024"; decimal commas ("11,2") are accepted
    as: days from: Read a duration as a number of days: "7 days", "x7d", "2 weeks", "1 month" (30 days), "14 dias"
    period_start: <column> as: days, or an integer value: Store the last day of a period of N days starting on that column's date: the date + N - 1. The column must be mapped before this one
    when: {attribute.<key>: [<label>, ...]} any source Use the source only when the attribute has one of these labels; otherwise try the next source
    concepts: {<label>: "<VOCABULARY>:<code>"} from: attribute.<key> Store the concept of the chosen label instead of the label
    maps_to: true concept: or concepts: Store the standard concept the code maps to
    lookup: <VOCABULARY> from: Find the text as a code of that vocabulary, e.g. units in UCUM
    map: {...} from: Code the text with the terminology mapper (see below)

    The table's id column (measurement_id, observation_id) is generated, numbered from id_start (default 1). Only top-level entities can have an omop block; a child's text is used from its parent with from: child.<key>.

    Fixed codes, standard concepts and domains

    Write codes as VOCABULARY:code, as they appear in the vocabulary, rather than as concept ids, so the file stays readable. They are looked up when the builder is created, and these fail before any model call:

    • a code that is not in the vocabulary;
    • a non-standard concept in a *_concept_id column. Add maps_to: true to use the standard concept it maps to;
    • a concept of a domain the column does not accept, e.g. a Condition concept in measurement_concept_id;
    • maps_to: true on a code without exactly one standard mapping.

    *_source_concept_id columns keep the code as written, standard or not, as the CDM asks. The ECOG definition shows why both exist:

          measurement_concept_id: {concept: "SNOMED:423740007", maps_to: true}
      measurement_source_concept_id: {concept: "SNOMED:423740007"}

    SNOMED 423740007 ECOG performance status is not standard; it maps to LOINC 89247-1 ECOG Performance Status score, which goes to measurement_concept_id, while the SNOMED concept is kept in measurement_source_concept_id.

    Standard, from any vocabulary

    A *_concept_id column needs a standard concept of the right domain. Its vocabulary does not matter: SNOMED, LOINC, RxNorm or any other. The rule applies to every source: fixed codes and label maps are checked when the builder is created, and a map or lookup that finds only a non-standard concept stores 0 and reports unmapped.

    Coding text with the terminology mapper

    Some concepts never change (body weight is always Body weight), but many depend on what the note says: the name of a lab test, a condition. A map source sends the extracted text to the same TerminologyMapper used for terminology mapping, which searches the vocabularies and picks the best standard concept.

    The predefined lab_results definition codes the test name this way:

          measurement_concept_id:
        from: text
        map: {}          # any standard concept of the column's domain (Measurement)

    The YAML says what to code. Your code chooses how, by configuring the mapper, because that involves search models, LLMs and API keys:

    import asyncio

from aatm.omop import ClinicalNote, OmopExtractionPipeline
from aatm.selectors import OpenAILLMSelector
from aatm.terminology_mapper import TerminologyMapper

mapper = TerminologyMapper(
    retriever="text-embedding-3-small",          # the embedding model chosen in `aatm init`
    selector=OpenAILLMSelector("gpt-5-mini"),    # an LLM picks among the candidates
)
mapper.retriever.top_k = 30                      # how many candidates it sees

pipeline = OmopExtractionPipeline("lab_results", model_id="openai/gpt-5-mini", mapper=mapper)
notes = [ClinicalNote(text="Labs 03/15/2025: Hb 11.2 g/dL, creatinine 1.4 mg/dl.", person_id=10)]
tables = asyncio.run(pipeline(notes))
tables.mappings_dataframe()

    mappings_dataframe() has one row per coded text, so you can review every choice:

    row_id column text method concept_id concept_name score stored
    1 measurement_concept_id Hb map 3000963 Hemoglobin [Mass/volume] in Blood 0.30 3000963
    1 unit_concept_id g/dL lookup 8713 gram per deciliter 8713

    How it works:

    • The search is limited to a domain, not a vocabulary. By default it is the domain the column requires (Measurement here). map: {domain: Condition} sets it explicitly, and map: {vocabularies: [LOINC]} narrows the search further if your data must use one vocabulary.
    • Each distinct text is coded once per run: a hundred notes mentioning "Hb" make one mapper query.
    • min_score (map: {min_score: 0.8}) stores 0 and reports low_confidence below that score. Scores depend on the retriever, so look at real scores in mappings_dataframe() before choosing a threshold.

    Review the mappings

    Short names are ambiguous. In a small test with nine lab results, the default selector, which takes the closest match, coded only 2 test names correctly; with OpenAILLMSelector choosing among 30 candidates, 7 of 9 were correct. Without a vocabulary filter, some tests map to general SNOMED procedures such as Potassium measurement rather than the more specific LOINC Potassium [Moles/volume] in Serum or Plasma; both are valid standard concepts.

    Searching with an agent

    The mapper makes one search with the text alone, then picks from what it found. That fails in two ways: the right concept is not among the candidates ("creatinine" brings back urine and 24-hour tests, but not serum creatinine), or the text does not say which variant it is, while the rest of the note does (mg/dL means a mass concentration, mmol/L a molar one).

    AgenticCoder codes each text with an LLM agent instead. The agent gets the text with its context, and searches the vocabularies with tools until it finds the concept or concludes there is none:

    import asyncio

from aatm.omop import AgenticCoder, ClinicalNote, OmopExtractionPipeline

coder = AgenticCoder(
    "openai/gpt-5-mini",                 # any aatm.llm model id
    retriever="text-embedding-3-small",  # the embedding model chosen in `aatm init`
    max_tool_calls=8,                    # per text
)
pipeline = OmopExtractionPipeline("lab_results", model_id="openai/gpt-5-mini", mapper=coder)
notes = [ClinicalNote(text="Labs 03/15/2025: Hb 11.2 g/dL, creatinine 1.4 mg/dl.", person_id=10)]
tables = asyncio.run(pipeline(notes))
tables.mappings_dataframe()[["text", "concept_name", "score", "rationale", "trace", "usage"]]

    The context. The builder gives the agent, for each coded text: the other values of the mention (its attributes, and the first text of each child, e.g. the value 1.4 and unit mg/dl of a lab test), the line of the note it comes from, and the target column (measurement.measurement_concept_id). The domain and vocabularies of the map source still restrict the answer. Nothing changes in the YAML.

    The tools.

    Tool What it does
    Semantic search The retriever's embedding search, with the agent's own queries: expansions ("Hb" → "hemoglobin"), translations ("potássio" → "potassium"), the specimen or unit added
    Lexical search Concept names and synonyms containing every word of a query, in .aatm/omop.db
    Code lookup A code in any vocabulary, with the standard concepts it maps to
    Concept details Synonyms, "Maps to" and the LOINC axes (component, property, time, system, scale, method), to check that the specimen and property match the unit
    Hierarchy Direct parents and children, to move to a more general or more specific concept

    The answer is checked against the vocabulary: it must be a standard, valid concept of the required domain and vocabularies, or the agent is asked again.

    What you get back. mappings_dataframe() gains three columns:

    • rationale: the agent's reason, e.g. "mg/dl is a mass concentration; serum is the usual specimen for creatinine";
    • trace: every action with its query and the candidates it returned;
    • usage: tool calls, LLM calls, input and output tokens, seconds, and whether the budget ran out.

    The score is the agent's confidence on a fixed scale, so min_score means the same thing whatever the retriever:

    Level Score Meaning
    high 0.9 Matches the text and everything the context states
    medium 0.6 The right concept, but a detail the context does not state was assumed
    low 0.3 The closest concept available, with a known mismatch or real ambiguity

    min_score: 0.5 keeps high and medium. When the budget runs out the agent must answer from what it has seen, and its score is capped at low.

    Caching. Within a batch, the plain mapper codes each distinct text once. The agent codes each distinct text in its context once: "creatinine 1.4 mg/dL" in two notes is one search, but "creatinine 1.4 mg/dL" and "urine creatinine 80 mg/dL" are two. To keep results across batches and runs, see Keeping results across runs.

    Choosing between the mapper and the agent

    On 30 lab results with gold LOINC codes (abbreviations, Portuguese names, 24-hour and urine tests; LOINC Measurement concepts only; text-embedding-3-small index; gpt-5-mini):

    Method Correct LLM calls per text Tokens per text (in / out)
    Nearest candidate (FirstResultSelector) 1 / 30 0 –
    OpenAILLMSelector over the top 30 14 / 30 1 not reported
    Agent, text only 27 / 30 2.2 3,300 / 940
    Agent, text with context 29 / 30 2.2 3,400 / 900

    The agent used 2.2 tool calls per text on average (at most 5 of the 8 allowed) and never ran out of budget. Its one miss was BUN, coded to urea nitrogen in blood rather than in serum or plasma. The LLM selector failed mostly because the right concept was not among its 30 candidates ("creatinine", "K", "potássio"). With context, the agent also told Hb (mass concentration, not "by calculation") and the albumin/creatinine mass ratio (from mg/g) apart.

    Most of the time per text goes to the vector search, not to the LLM: a ChromaDB query filtered by domain takes about 5 seconds on a full index (2.5 million expressions), against a few milliseconds unfiltered.

    The benchmark and its gold codes are in benchmarks/concept_search/; run it with your own retriever and model before choosing.

    • The plain mapper costs one search (and one LLM call with an LLM selector) per distinct text, and is the choice when texts are explicit ("Creatinine in serum") or cost and speed matter most.
    • The agent costs a few LLM calls per distinct text in context, and is the choice when texts are short, abbreviated or not in English, and when variants of a test differ by specimen or unit.

    The agent is also available as the selector of a TerminologyMapper, so CSV terminology mapping and a mapper you already configured can use it: TerminologyMapper(retriever=..., selector=AgenticSelector("openai/gpt-5-mini")). In a builder, that mapper also receives the context.

    Keeping results across runs

    Coding is usually the most expensive step. Without a cache, every batch and every rerun (after a crash, or to rebuild the tables after changing a mapping) pays for the same texts again. Turn on the coding cache to store each result on disk and reuse it:

    from aatm.omop import CodingCache, OmopExtractionPipeline

pipeline = OmopExtractionPipeline(
    "lab_results", model_id="openai/gpt-5-mini", mapper=coder, cache=True
)
tables = await pipeline(notes)
tables.cache_stats  # CacheStats(hits=..., misses=..., stored=...), and .hit_rate
    cache= Effect
    None or False (default) No cache
    True .aatm/coding_cache.db
    "path/to/cache.db" That file
    CodingCache(path, max_entries=..., max_bytes=...) That file, with a size limit

    The same argument works on OmopTableBuilder. In mappings_dataframe(), cached tells which concepts came from the cache; their usage was spent in the run that first coded them.

    A result is only reused for exactly the same input. The cache never changes what a run produces:

    • The agent (and a mapper with AgenticSelector) reads context, so its key is the text with its full context: the related values (such as the lab value and unit), the line of the note and the target column. "Hb 11.2 g/dL" in two notes with the same line is one search; the same "Hb" on a different line is searched again. Hits therefore come from reruns, rebuilds and repeated lines (templated notes), rather than from the same text in different notes.
    • The plain mapper ignores context, so its key is the text, domain and vocabularies: each distinct text is coded once, across all runs.
    • Every key includes the coder's identity: its class, models, generation settings, retriever and index, tool budget, the agent's prompts, the server URL of OpenAI-compatible providers and the aatm version. Changing any of these, or upgrading aatm, starts from an empty cache for that coder. The old entries stay in the file until they are evicted or cleared.
    • The identity also covers the data the coder reads: the vocabulary releases in the vocabulary database (e.g. LOINC 2.78) and its size, and the id and size of the ChromaDB collection. Rebuilding either from other data starts from an empty cache, and a warning names the old entries so you can clear them.
    • Results that ended in an error (e.g. an API failure) are not stored, so they are retried on the next run.

    Each batch codes its most frequent texts first and writes results as it goes, so a run that stops partway keeps what it paid for.

    Size. By default the cache grows without limit. Set max_entries (results kept) or max_bytes (bytes of results kept; the file is somewhat larger) to cap it. When a write goes over a limit, the entries used least recently are deleted first:

    cache = CodingCache(".aatm/coding_cache.db", max_entries=1_000_000, max_bytes=2 * 1024**3)

    Clearing. Delete everything and shrink the file, or one coder's entries:

    cache.info()   # entries, size on disk, and the coders they belong to
cache.clear()  # everything
cache.clear(coder="<hash from info()>")

    or from the command line:

    aatm cache info
aatm cache clear            # asks for confirmation; --yes to skip it
aatm cache clear --coder <hash>

    Rebuilt data the cache cannot see

    The data of a retriever that is not a ChromaDB collection (a retriever of your own, for example) cannot be fingerprinted. When the cache opens, a warning names such components: changes to the content of ... cannot be detected. If you rebuild their index, run aatm cache clear, or results coded against the old data will be reused without any error.

    Model aliases are another blind spot: openai/gpt-5-mini names whatever the provider currently serves under that name. Pin a dated model version when results must stay reproducible, and clear the cache when you change it.

    Custom coders. A coder of your own is cached when it has a cache_identity() method returning JSON-compatible values that cover everything that changes its results. Otherwise wrap it yourself and say what it is: CachedCoder(my_coder, cache, identity={"name": "my_coder", "version": 2}).

    Rate limits for long runs

    No rate limits are set by default: the pipeline sends model calls as fast as it can, and retries rate-limit and transient errors on its own. For large datasets, or a provider quota you must stay under, set limits once before the run; they cover extraction and coding together:

    from aatm.llm import set_rate_limits

set_rate_limits("openai", max_concurrency=32, requests_per_minute=5000)

    See Rate limits and retries for every option.

    Code lookups

    lookup: <VOCABULARY> finds the extracted text as a code of a vocabulary. It suits units: "g/dL" is the UCUM code of gram per deciliter. An exact match wins; otherwise a single standard concept matching while ignoring case is used ("mg/dl" → mg/dL). Texts that are not codes, such as "lb" or "x10^3/uL", are reported as unmapped.

    The observation table

    The observation table holds facts that are not measurements, conditions, procedures, drugs or devices: smoking, family history, social and lifestyle facts. Each row pairs an observation_concept_id (what was observed) with a value: a concept, a number, a text or a date.

    Several definitions can run together, so each note is sent to the model only once:

    import asyncio

from aatm.omop import ClinicalNote, OmopExtractionPipeline
from aatm.selectors import OpenAILLMSelector
from aatm.terminology_mapper import TerminologyMapper

mapper = TerminologyMapper(retriever="text-embedding-3-small", selector=OpenAILLMSelector("gpt-5-mini"))
mapper.retriever.top_k = 30

pipeline = OmopExtractionPipeline(
    ["smoking_status", "family_history", "medical_history"],  # names, YAML paths, or both
    model_id="openai/gpt-5-mini",
    mapper=mapper,  # family_history and medical_history code conditions with it
)
notes = [
    ClinicalNote(
        text=(
            "Former smoker, 30 pack-years. Mother had breast cancer at 45. "
            "History of appendicitis."
        ),
        person_id=20,
        note_date="2025-06-01",
    ),
]
tables = asyncio.run(pipeline(notes))
tables["observation"]

    A typical result (concept names added in italics):

    observation_id observation_concept_id observation_source_value value_as_number value_as_concept_id value_source_value qualifier_concept_id unit_concept_id
    1 43054909 Tobacco smoking status Former smoker 45883458 Former smoker former
    2 3003421 Cigarettes smoked total (pack per year) 30 pack-years 30.0 30 0
    3 4167217 Family history of clinical finding breast cancer 4112853 Malignant tumor of breast breast cancer 4248584 Mother
    4 3002660 History of Past illness Narrative appendicitis 440448 Appendicitis appendicitis

    smoking_status gives up to two rows per mention:

    • Smoking status, with the status as a concept in value_as_concept_id: never, former, current every day, current some day, or current without a frequency. "Non-smoker" or "denies smoking" do not say whether the patient ever smoked, so they get the label not_current, stored as 0 and reported as unmapped_label.
    • Pack-years, with the number in value_as_number. UCUM has no code for pack-years, so unit_concept_id is 0 and unit_source_value is "pack-years".

    family_history follows the CDM convention for family history: observation_concept_id is Family history of clinical finding, value_as_concept_id is the condition, coded by the mapper, and qualifier_concept_id is the relative (Mother, Sister...). The CDM has no column for the relative, so that last choice is a convention of this definition; qualifier_source_value keeps the label.

    medical_history takes the patient's past conditions, which the CDM keeps out of condition_occurrence: "history of appendicitis", "h/o stroke, no sequelae", "hepatitis C, treated and cured". observation_concept_id is LOINC 11348-0 History of Past illness Narrative and value_as_concept_id is the condition, coded by the mapper, as for family history. Conditions the patient still has, even when listed under past medical history ("PMH: hypertension"), go to condition_occurrence, and past surgeries ("s/p appendectomy") are not extracted. When the past condition happened is not captured: observation_date is the note date.

    Why LOINC 11348-0

    SNOMED History of clinical finding in subject is not a standard concept. The vocabulary maps precoordinated SNOMED concepts such as History of myocardial infarction to the condition with Maps to value. Their Maps to target is in the OMOP Extension vocabulary, which the other predefined definitions do not need. To use a different concept, copy medical_history.yaml and change observation_concept_id.

    Which concepts the observation table accepts

    The CDM sends Condition, Procedure, Drug, Measurement, Device and Specimen concepts to their own tables, so observation_concept_id rejects them. value_as_concept_id accepts any domain: for family history it holds a condition.

    When you combine definitions, every entity key must be unique. A clash fails with a message naming the files:

    Entity keys must be unique across the combined definitions, since the model's output is matched to definitions by key:
  - key 'smoking_status' is defined in predefined 'smoking_status' and definitions/alcohol_use.yaml
List each file once, and rename keys that clash in your own files.

    The condition_occurrence table

    The condition_occurrence table holds the patient's diagnoses, problems, signs and symptoms. Each row is one mention of a condition, with its standard concept, its dates and a status.

    import asyncio

from aatm.omop import ClinicalNote, OmopExtractionPipeline
from aatm.selectors import OpenAILLMSelector
from aatm.terminology_mapper import TerminologyMapper

mapper = TerminologyMapper(retriever="text-embedding-3-small", selector=OpenAILLMSelector("gpt-5-mini"))
mapper.retriever.top_k = 30

pipeline = OmopExtractionPipeline(
    "condition_occurrence",
    model_id="openai/gpt-5-mini",
    mapper=mapper,  # codes condition names
)
notes = [
    ClinicalNote(
        text=(
            "Type 2 diabetes since 2019. Probable community-acquired pneumonia. "
            "History of appendicitis. Rule out PE. Denies chest pain. "
            "Mother had breast cancer."
        ),
        person_id=20,
        note_date="2025-06-01",
    ),
]
tables = asyncio.run(pipeline(notes))
tables["condition_occurrence"]

    A run with gpt-5-mini gave two rows (concept names added in italics):

    condition_occurrence_id condition_concept_id condition_source_value condition_start_date condition_status_concept_id condition_status_source_value condition_type_concept_id
    1 201826 Type 2 diabetes mellitus Type 2 diabetes 2019-01-01 32893 Confirmed diagnosis confirmed 32858 NLP
    2 4293463 Community acquired pneumonia community-acquired pneumonia 2025-06-01 32899 Preliminary diagnosis preliminary 32858 NLP

    The only issue is imputed_date_parts on row 1: "2019" has no month or day and is read as 2019-01-01.

    What is not a row. The definition follows the CDM conventions for this table, so the other four conditions of the note are left out:

    In the note Why it is not here
    "History of appendicitis" Past diagnoses belong in observation, says the CDM: add medical_history to the list of definitions to keep it. Long-standing conditions the patient still has, e.g. "PMH: hypertension", are kept.
    "Rule out PE" Rule-out and "question of" diagnoses are not recorded in this table.
    "Denies chest pain" Negated.
    "Mother had breast cancer" Family history belongs in observation: add family_history to the list of definitions to keep it.

    Status. Each condition gets a required status label, stored in condition_status_concept_id:

    Label Means Concept
    confirmed Stated as a fact, e.g. "hypertension", "diagnosed with asthma in 2010" 32893 Confirmed diagnosis
    preliminary A likely working diagnosis, e.g. "probable pneumonia", "presumed sepsis" 32899 Preliminary diagnosis

    The CDM's own examples of a status are the point in the visit when the diagnosis was given (admitting, principal, secondary diagnosis). Notes rarely say that, so it is not extracted.

    Dates. condition_start_date is the first that applies:

    1. the start date the note gives for that condition ("since 2019" → 2019-01-01, reported as imputed_date_parts);
    2. the note date. The condition is known to be present then, but may have started much earlier, so read these start dates as "recorded on" rather than "onset".

    When the note gives only an end date before the note date ("pneumonia, resolved 2024-04-10"), that date is used for both start and end, as the CDM allows for a single date, and reported as single_date.

    The CDM notes that most sources have no condition start date, and records most conditions as snapshots without an end date. condition_end_date is the end date the note gives, e.g. for an episode in a discharge summary ("pneumonia from 03/01/2025 to 03/10/2025"). An end date before the start date is left empty and reported as invalid_value.

    Which concepts the condition_occurrence table accepts

    condition_concept_id takes standard concepts of the Condition domain only. The mapper searches that domain, and a concept of another domain, e.g. a procedure, is stored but reported as domain_mismatch. Check the coded conditions with tables.mappings_dataframe().

    The drug_exposure table

    The drug_exposure table holds the drugs a patient is prescribed, is given or takes: medicines, vaccines and biologics. Each row is one mention of a drug, with its standard concept, its dates, the route and the dosing instructions. The predefined definition follows the CDM conventions for this table and the THEMIS conventions for drug_exposure.

    import asyncio

from aatm.omop import ClinicalNote, OmopExtractionPipeline
from aatm.selectors import OpenAILLMSelector
from aatm.terminology_mapper import TerminologyMapper

mapper = TerminologyMapper(retriever="text-embedding-3-small", selector=OpenAILLMSelector("gpt-5-mini"))
mapper.retriever.top_k = 30

pipeline = OmopExtractionPipeline(
    "drug_exposure",
    model_id="openai/gpt-5-mini",
    mapper=mapper,  # codes drug names
)
notes = [
    ClinicalNote(
        text=(
            "Home meds: lisinopril 10 mg PO daily since 2020, metformin 500 mg tablet BID.\n"
            "Ceftriaxone 1 g IV given in the ED.\n"
            "Plan: start amoxicillin 875 mg PO BID for 7 days. Consider a statin.\n"
            "Allergic to penicillin. Not on anticoagulation."
        ),
        person_id=30,
        note_date="2025-06-01",
        visit_occurrence_id=900,
        provider_id=12,
    ),
]
tables = asyncio.run(pipeline(notes))
tables["drug_exposure"]

    A run with gpt-5-mini gave four rows (concept names added in italics; drug_type_concept_id is 32858 NLP in every row):

    drug_exposure_id drug_concept_id drug_source_value start end route_concept_id sig visit_occurrence_id provider_id
    1 1308304 lisinopril 10 MG lisinopril 10 mg 2020-01-01 2025-06-01 4132161 Oral
    2 40164929 metformin hydrochloride 500 MG Oral Tablet metformin 500 mg tablet 2025-06-01 2025-06-01
    3 46287328 ceftriaxone 1000 MG Injection Ceftriaxone 1 g 2025-06-01 2025-06-01 4171047 Intravenous 900 12
    4 19083494 amoxicillin 875 MG amoxicillin 875 mg 2025-06-01 2025-06-07 4132161 Oral 875 mg PO BID for 7 days 900 12

    "Consider a statin" is only considered, the penicillin is an allergy and anticoagulation is negated, so none of them is a row. Drug classes such as "antihypertensives" are left out too: the CDM would store them with drug_concept_id = 0.

    Kind. Each drug gets a required kind label, which decides the end date and the visit:

    Label Means Visit and provider
    administered Given to the patient, e.g. "ceftriaxone 1 g IV given in the ED" From the note
    prescribed Started, prescribed or changed in this note, e.g. "start amoxicillin" From the note
    taking On the patient's medication list, or reported use Left empty: the CDM fills the visit only when the exposure was started in it

    Dates. drug_exposure_start_date is the start date the note gives, else the note date. drug_exposure_end_date is required by the CDM; when the note gives none, it is inferred as THEMIS ratified:

    1. the end date the note gives ("until 06/10/2025"), also kept in verbatim_end_date;
    2. the start date + the planned duration - 1 day ("for 7 days" → 2025-06-07);
    3. for a prescribed drug, the start date + 29 days;
    4. for a taking drug, the note date: the last date it is known to be taken. THEMIS has no rule for medication lists, so this is a convention of this definition;
    5. for an administered drug, the start date.

    When the note gives only a stop date before the note date ("aspirin stopped on 05/01/2025"), that date is used for both start and end and reported as single_date, rather than a start after the stop.

    Route. The optional route label (oral, intravenous, subcutaneous, inhaled, ...) is stored as its standard SNOMED route concept in route_concept_id.

    Not filled. The CDM fills days_supply only from a verbatim days supply, never from other fields, so a duration in a note does not go there. quantity, refills, stop_reason and lot_number are left empty, and dose_unit_source_value is a legacy column the CDM plans to deprecate.

    Check the coded drugs

    drug_concept_id takes standard concepts of the Drug domain. The CDM prefers the most detailed concept the source supports, such as a clinical drug, over an ingredient, so the mention keeps the strength and dose form. A name without detail can be coded too specifically: in one run "Influenza vaccine" was coded as one seasonal formulation, with a score of 0.41. Review low scores with tables.mappings_dataframe().

    The device_exposure table

    The device_exposure table holds the medical devices a patient has or is given: implants (pacemakers, stents, artificial joints), equipment and supplies (crutches, catheters, insulin pumps, CPAP) and materials such as sutures. Each row is one mention of a device, with its standard concept, its dates and the number of devices. The predefined definition follows the CDM conventions for this table; THEMIS has no device conventions.

    import asyncio

from aatm.omop import ClinicalNote, OmopExtractionPipeline
from aatm.selectors import OpenAILLMSelector
from aatm.terminology_mapper import TerminologyMapper

mapper = TerminologyMapper(retriever="text-embedding-3-small", selector=OpenAILLMSelector("gpt-5-mini"))
mapper.retriever.top_k = 30

pipeline = OmopExtractionPipeline(
    "device_exposure",
    model_id="openai/gpt-5-mini",
    mapper=mapper,  # codes device names
)
notes = [
    ClinicalNote(
        text=(
            "s/p PCI with 2 drug-eluting stents in 2021. Dual-chamber pacemaker since 2019.\n"
            "Foley catheter inserted today for retention. Walks with crutches.\n"
            "No indwelling lines. Candidate for ICD. Nicotine patch 21 mg daily."
        ),
        person_id=40,
        note_date="2025-06-01",
        visit_occurrence_id=950,
        provider_id=14,
    ),
]
tables = asyncio.run(pipeline(notes))
tables["device_exposure"]

    A run with gpt-5-mini gave four rows (concept names added in italics; device_type_concept_id is 32858 NLP in every row):

    device_exposure_id device_concept_id device_source_value start end quantity visit_occurrence_id provider_id
    1 4131681 Drug eluting stent drug-eluting stents 2021-01-01 2
    2 40481477 Dual chamber pulse generator, device Dual-chamber pacemaker 2019-01-01 1
    3 40625746 Foley catheter Foley catheter 2025-06-01 1 950 14
    4 4251933 Crutch crutches 2025-06-01 1

    The PCI is a procedure, the action of placing the stents: only the stents are a device. "No indwelling lines" is negated, the ICD is only considered, and the nicotine patch is a drug, which belongs in drug_exposure. So none of them is a row.

    Kind. Each device gets a required kind label:

    Label Means Visit and provider
    placed Implanted, inserted, applied, prescribed or supplied in this encounter, e.g. "Foley catheter inserted today" From the note
    existing The patient already has or uses it, e.g. "has a pacemaker", "walks with crutches" Left empty: the CDM fills the visit only when the exposure was started in it

    Dates. device_exposure_start_date is the date the note gives (e.g. the implant date, "since 2019" → 2019-01-01, reported as imputed_date_parts), else the note date. Unlike drug_exposure, the end date is optional, and the CDM fills it only when the source gives it, so it is never inferred. When the note gives only a removal date ("PICC line removed on 05/20/2025"), it is used for both dates and reported as single_date.

    Quantity. The number the note gives ("2 drug-eluting stents"), else 1: the CDM stores 1 when a device exposure exists without a quantity.

    Not filled. unique_device_id and production_id (the UDI, rarely written in notes), the unit columns, which the CDM leaves NULL when the source has no unit, and the datetime columns.

    Check the coded devices

    device_concept_id takes standard concepts of the Device domain. Device names in notes are often short ("CPAP", "brace"), and mapper scores were low even for right answers in our runs, e.g. "left knee brace" → Knee orthosis at 0.31. Review them with tables.mappings_dataframe() before setting a min_score.

    Processing large datasets

    await pipeline(notes) holds every note and row in memory, and a failure partway loses the model calls already made. For a full dataset, use pipeline.run: it reads the notes in chunks, writes each chunk's rows to Parquet files as it goes, and records its progress, so a run that stops can be resumed.

    import asyncio
from aatm.omop import OmopExtractionPipeline, OmopRun

pipeline = OmopExtractionPipeline(
    "ecog_performance_status",
    model_id="openai/gpt-5-mini",
    max_concurrency=16,  # notes extracted at once
    cache=True,          # code each distinct text once, across chunks and runs
)
summary = asyncio.run(
    pipeline.run(
        "notes.parquet",               # or .csv, a folder of Parquet files, a DataFrame...
        "output/ecog",
        chunk_size=200,
        columns={"note_text": "text"}, # source column -> ClinicalNote field
    )
)
print(summary)  # notes built, skipped and failed, rows per table, cache hit rate

    Sources. A CSV or Parquet file, a folder of Parquet files, a DataFrame, an iterable of ClinicalNote objects or dicts, or a database query:

    import sqlite3
from aatm.omop import notes_from_sql

con = sqlite3.connect("cdm.db")  # or a SQLAlchemy engine for other databases
source = notes_from_sql(
    "SELECT note_id, note_text AS text, person_id, note_date, visit_occurrence_id "
    "FROM note WHERE note_date >= '2024-01-01'",
    con,
)
summary = await pipeline.run(source, "output/ecog")

    Columns that are not ClinicalNote fields are ignored. Every note needs a unique note_id: it is how a resumed run knows what is done.

    Reading the output. Each table, and the provenance, issues and mappings of its rows, is a folder of Parquet files:

    run = OmopRun("output/ecog")
run.table("measurement")    # a DataFrame
run.provenance()            # note_id, entity_id and span of each row (table, row_id)
run.issues()
run.mappings()
run.failures()              # notes that could not be extracted or built, and why
run.status()                # {"built": 9850, "failed": 3}
run.dataset("measurement")  # a pyarrow Dataset, to filter without loading it all

    DuckDB, Polars and Spark read the folders directly, e.g. SELECT * FROM 'output/ecog/measurement/*.parquet'.

    Resuming. Run the same call again. Notes already built are skipped; notes extracted but not yet written are built from their stored extraction result, without another model call. A note that fails (an API error once retries are spent, a result that cannot be built) is recorded with its error and the run goes on; the next run tries it again, up to max_attempts times in all (3 by default).

    Changing the mappings. Extraction results are stored apart from the tables (in output/ecog/ledger.db). After editing an omop block, rebuild the tables from them, with no extraction calls:

    await pipeline.rebuild("output/ecog")

    A run refuses to add rows built with other mappings to an existing folder until you rebuild, and refuses a folder made with other entity definitions or another extractor: use a new folder for those.

    Watching a long run. A progress line is logged every log_every seconds (60 by default), when a chunk is done:

    Progress: 12,400 of 100,000 notes done (12.4%) in 41m10s, 301 notes/min; about 4h17m left;
12,380 built, 0 skipped, 20 failed; 31,950 LLM calls, 48,210,330 tokens; cost 14.2031;
cache hits 63%

    The time left needs the number of notes in the source. It is read from Parquet files, DataFrames and lists; for a CSV file or a query, pass total=. Logs are shown with aatm.logs.configure_logging().

    At the end, the summary breaks the run down by stage (extraction, coding and building): notes or texts handled, time, errors, LLM calls and tokens per model. Give your models' prices, per million input and output tokens, to estimate the cost:

    summary = await pipeline.run(
    "notes.parquet",
    "output/ecog",
    prices={"openai/gpt-5-mini": (0.25, 2.00)},  # check your provider's current prices
)
summary.stages["extraction"].usage.by_model  # calls and tokens per model
summary.stages["coding"].cost                # coding is the agent's calls, if any
summary.cost

    Each run and rebuild also saves its summary as JSON in output/ecog/runs/. The file is updated at every progress line, so you can follow a run from another process, and it is kept with completed: false and the error when a run stops. OmopRun("output/ecog").summaries() reads them back, oldest first.

    Row ids. The primary keys of a run are derived from the note: note_id * 65536 + n, where n is the position of the mention in the note. The same note gets the same ids in any chunk, after a resume or a rebuild, and in separate runs over parts of a dataset; ids never repeat across tables. They need a 64-bit (BIGINT) column. OmopTableBuilder.build(..., row_ids="note") numbers rows the same way.

    Speed and cost

    max_concurrency (default 1) sets how many notes are extracted at once; set rate limits to stay under your provider's quota. With cache=True, a text seen in an earlier chunk or run is not coded again. chunk_size bounds memory; larger chunks let the builder group more repeated texts per coding call.

    While a chunk is built (coded and written), the next one is extracted, so the slower of the two stages sets the pace. This pays off when coding takes about as long as extraction, e.g. with the agent; without a mapper, building takes milliseconds and extraction is all the time. At most two chunks are in memory. The two stages share the per-minute rate limits, but each gets its own max_concurrency, so up to twice as many calls may be in flight.

    Current limits

    • Only the measurement, observation, condition_occurrence, drug_exposure and device_exposure tables are supported so far.
    • drug_exposure end dates are not inferred from the quantity and daily dose (the second THEMIS rule), and mail-order prescriptions are not told apart from others.
    • condition_start_date falls back to the note date when the note gives no date, which is later than the real onset of long-standing conditions.
    • With the plain mapper, map searches with the extracted text alone: a unit such as mg/dL, which hints at a serum test, is only used by the agent.
    • Mapper scores are not comparable across retrievers and selectors. The agent's score is a self-reported confidence level, not calibrated yet.
    • Units written outside UCUM ("lb", "x10^3/uL", "mEq/L") are not converted before the lookup.
    • Relative dates ("on admission", "after cycle 2") are not resolved: the next source, usually the note date, is used and the issue is reported.
